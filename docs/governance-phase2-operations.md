## Requested scope

Resolutions, meeting management, approvals, agenda records, minutes, action assignments and notifications. Governing-document and signature-authority information remains unverified, therefore the software stores *reported voting outcomes* separately from *legally adopted and published governing instruments*.

### Actual implementation

* Meetings: draft, agenda prerequisites, scheduled, then recorded as held with attendance count and evidence reference. Stored in ino_gov_meetings.
* Agendas: sequenced, immutable-after-scheduling items; no silent replacement of the agenda packet. Stored in ino_gov_agenda.
* Minutes: append-only text revisions for held meetings, source reference, independent reviewer, no overwriting. Stored in ino_gov_minute_versions.
* Resolutions: immutable motion text and source authority citation; separate reviewer; optionally linked to a documented meeting. Stored in ino_gov_resolutions.
* Approval evidence: only a reviewer-independent publisher can record a reported carried/not carried/tabled outcome. Recording requires reviewed resolution, held meeting, newest reviewed minutes, recorded attendance, votes and abstentions, quorum basis, decision evidence reference and explicit attestation. Status = outcome_recorded (NOT adopted).
* Action assignments: titled work related to an actual meeting or resolution, assigned to a WordPress user with existing governance-view permission; only the assignee can complete with a documented note. Stored in ino_gov_actions.
* Notifications: private, durable in-app task-assignment inbox, read/unread handling with per-recipient authorization. Stored in ino_gov_notifications. Email, SMS, calendar pushes and future reminder schedules are NOT implemented in this version.
* Operations audit: source-attributed creation, status change, reviews, decisions, completions, created_at; logged in ino_gov_ops_events. State transitions are conditional and use a transaction to pair the audit with changes, requiring an InnoDB-capable site database for reliable atomic rollback.

All tables use WordPress site table prefix and are introduced via dbDelta guarded by ino_gov_ops_schema_version.

## Access / roles

* ino_governance_edit: create draft meetings, agenda items, submit minutes/resolutions, assign actions, schedule and record meeting held.
* ino_governance_review: independent review of minutes and resolution proposals. No author self-review.
* ino_governance_publish: record reported decision evidence, excluding same reviewer, but no legal-adoption action.
* ino_governance_view: restricted dashboard (including minutes, motion text and governance audit) and private notices. An assignee must have this permission.
* Assigned user: mark their own task complete and their own notification read (nonce and ownership checks).
* Public/ordinary member: NO access to meeting packets, draft resolutions, internal minutes, action details, audit or notices.
* Site administrator: platform setup and draft editing by existing Phase 1 rules; does not gain reviewer/publisher authority merely because of administrator status.

Technical WordPress admin access cannot itself prove constitutional authority. Role assignments still require separate documentary delegation.

## Security invariants

* No resolution adoption generated by the application. Reported carried/not-carried outcomes do NOT imply adopted law, constitutional validity, officer authority, governmental recognition or external tribal status.
* No approval without independent review, a documented held meeting, latest minutes reviewed, votes within recorded attendance, rule/authority text and explicit officer attestation.
* No authority threshold is invented; legal/quorum rules must be supplied and validated outside this plugin before any public adoption workflow.
* No private documents are uploaded or exposed from WordPress public Media Library.
* Mutating operations use logged-in roles, WordPress nonces, fixed operations and statuses, and server-side record existence/relationship checks.
* Assignment notifications include only generic text (no confidential detail) and are readable only by the recipient.
* No automated email/broadcast is sent. Staff must not assert notifications were emailed.
* Page uses real database counts; no mock approval statistics or invented meetings/resolutions.

## Remaining release gates / manual test plan

1. Confirm exact-head PHP 7.4/8.1/8.3 lint, source contract checks and no naming collisions with older plugins.
2. WordPress staging: upgrade older installs and reproduce both Phase 1 and Phase 2 schema migrations; confirm table indexes/constraints; **ensure all new tables are InnoDB**.
3. Test with empty tables and populated tables. Verify reporting totals and audit counts match stored rows.
4. Role matrix: anonymous, member, governance reader, records officer, reviewer, publisher and administrator. Attempt every direct admin-post action without nonce, without required capability, and with another recipient's notice or task.
5. Meeting: create → agenda → schedule → held; attempt schedule without agenda, wrong state, invalid meeting date, and attendance of zero.
6. Minutes: first revision submission, independent review, second revision after review, latest-version gate, concurrent revision attempts.
7. Resolution: create with source and optionally meeting, independent review, decision recorded. Reject a self-review, self-recording as same reviewer, a missing meeting, unreviewed latest minutes, votes exceeding attendance, empty rule evidence, missing attestation.
8. Verify a carried outcome remains only outcome_recorded in internal registry. **It must not become a Phase 1 published Constitution/resolution or be labelled adopted.**
9. Task: reject assignment to nonexistent/non-governance user and invalid source. Confirm in-app notice insert and only assigned user can mark complete; per-recipient read authorization.
10. Verify no private contents in cached anonymous pages, shortcode responses, frontend/REST APIs, media URLs or public WordPress search.
11. Verify UI at 320/768/1440px; keyboard, screen reader, focus, contrast, reduced-motion and WPBakery compatibility.
12. Confirm notification-inbox and audit logs are not leaked in server or app logs and that daily backups/retention policy exist.
13. Review adopted Constitution, signatory roster, quorum and voting rules, and formal governance record publication procedure with INO authorized leaders and counsel.
14. Merge base security PR #12, UI PR #13 and Phase 1 PR #14 first, rebase Phase 2, then retest exact head before staging rollout. No production deploy is authorized by this PR.
